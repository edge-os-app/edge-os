## 1. What the relay changes

Before: the accepted transport job runs Hermes, the transport and a credential copy in one process (`docs/qualification/hermes-job-support/README.md` section 1). Now: the Hermes job has no credential mount and no network; its one admitted request goes as a file into its own output folder; a separate relay container, inside the AUTHORED provider's loopback-only network namespace (CONTRACT amendment A4), checks a host-signed grant, runs the accepted guard again on the exact bytes, records a start before the one HTTPS request, and returns a bounded reply. The relay's records and the provider's receipts count requests outside the job. Details: `CONTRACT.md`.

- `test_relay_admission.py` (no Docker): grants are signed over every identity; a grant changed after signing (another owner, request, attempt or expiry), signed with another key, for another release, expired or not yet valid admits nothing; channel messages with another attempt, route or release, any extra field (URL, header, credential), a body that is not base64 or too large are refused; ACTUAL releases cannot be expressed.
- `test_relay_turn_runner.py` (no Docker): construction does no I/O; ACTUAL routes refused with or without a release; no grant without a recorded reservation, a proved owner/request and a live relay of the same release (all released, no job); an existing grant is never replaced (UNKNOWN); a zero-request result is released only with the relay's closed-not-started record; any job report the relay record does not support (hidden request, phantom request, other usage, a non-2xx or missing status, lost reply, no close record) is withheld as UNKNOWN with the full reservation; a raising job still revokes its grant.

- `test_relay_egress_probe.py` (no Docker): the relay's probe records how a connection ended: a listening port `connected`, a closed port `refused` (an answer, never "blocked"), an unknown name `dns_failure`.
- `test_relay_application_refusals.py` (no Docker): `open_relay_mount` refuses production, another interpreter, ACTUAL and a mismatched policy before any engine.
- `test_relay_through_pinned_hermes.py` (ACTUAL pinned Hermes, Docker): one request through the relay, every identity equal to the attempt, the provider sees the relay's bearer and none of Hermes' headers, exact charge, relay usage equals job usage; job guard refusal released on the relay's closed-not-started record; relay down: no grant, no job, released; lost, oversized, redirect, provider error and missing usage keep the full reservation with relay and provider counts (1, 1); a hung provider is cut at the grant expiry and the job at D; a relay crash after the request never resends; two attempts at once keep their own grants and charges; a hostile job finds no key file or key environment and connects to nothing (localhost:8443, the relay's name, 1.1.1.1, host), and its altered model/route/release/attempt/header/URL/oversized channel messages are refused before any request, its duplicate sent once; the provider runs with `--network none` and the relay with `container:<provider id>`: one namespace (same id in both kernels), `lo` the only interface up, no IPv4 route, no IPv6 route outside `lo`, no published port, exact mounts, and the heartbeat probe connects to the provider; with positive controls before and after (an owned listener on an owned bridge, `host.docker.internal` and its Docker Desktop address through a port published on host 127.0.0.1 only, all `connected` from a control container), the relay sees `unreachable` for every address and `dns_failure` for the name; bridge gateways are recorded but a control container gets `refused` there, so they support no claim; a relay whose provider died keeps loopback only and the provider address refuses, and a new container under the provider's name is never joined (the relay restart fails); a host killed mid-turn is recovered within C, its grant closes at expiry, its reservation stays and blocks its scope; no evidence, record or log holds the key.

## 3. How to check

From `apps/api`, with the locked environment. Use `.venv/bin/python -m pytest`: a cloned environment's `pytest` script can start another checkout's interpreter.

```
.venv/bin/python -m pytest -p no:cacheprovider -q ../../tests/hermes_provider_relay/test_relay_admission.py ../../tests/hermes_provider_relay/test_relay_turn_runner.py ../../tests/hermes_provider_relay/test_relay_service.py ../../tests/hermes_provider_relay/test_relay_transport.py ../../tests/hermes_provider_relay/test_relay_application_refusals.py ../../tests/hermes_provider_relay/test_relay_egress_probe.py
HERMES_RELAY_EVIDENCE_DIR=<private folder> .venv/bin/python -m pytest -p no:cacheprovider -q ../../tests/hermes_provider_relay
```

The second command needs Docker and the pinned Hermes checkout (see `docs/qualification/hermes-job-support/README.md` section 4). It builds the pinned image, starts its own relays, providers, control listener and control bridge by exact name and label, and removes them; `relay-cleanup.json`, `app-relay-cleanup.json` and `image-cleanup.json` in the evidence folder must show nothing left. About five minutes.
